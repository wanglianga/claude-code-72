# 邻里共享厨房 · 预约与卫生巡检平台

面向社区共享厨房的一体化管理页面：居民 / 社团 / 公益组织**预约**，管理员**使用前核验**，五类角色围绕同一次使用记录**协同处理使用中事件**，结束时管理员**七项逐项验收并决定押金**，社区按活动类型、设备损耗、清洁超时与投诉**复盘运营效果**。

技术栈：**Vue 3 + TypeScript + Pinia + Vite**，生产镜像为多阶段构建的 nginx（非 root + HEALTHCHECK），纯前端、浏览器本地持久化（localStorage），无需数据库即可完整体验全部业务流。

---

## 原始需求

> 设计社区邻里厨房预约与卫生巡检页面，可使用 Vue 3、TypeScript 和 Pinia。居民、社团或公益组织预约共享厨房时，页面记录使用人数、烹饪类型、是否油炸、食材暂存、设备需求、活动性质、负责人和押金。预约成功后，页面展示可用灶台、烤箱、冰箱、消毒柜、餐具、垃圾分类点和清洁要求。使用前，管理员核验预约人、健康承诺、食材存放和设备状态；使用中，可能出现油烟过大、设备损坏、邻里投诉、食材混放、临时加人或活动超时。页面要让预约人、管理员、保洁、维修和社区工作人员围绕同一次使用记录处理。结束时，管理员按灶台、台面、冰箱、垃圾、地面、餐具和设备逐项验收，决定押金退还、扣费、补清洁或限制后续预约。社区复盘时，可以按活动类型、设备损耗、清洁超时和投诉查看共享厨房运营效果。页面还要支持活动前检查、现场拍照、押金争议、公益活动免押、食品安全告知和社区公示。共享厨房既是居民服务也是公共空间，页面要能让管理员看清一次使用对卫生、邻里关系和设备寿命的影响。对公益课堂、邻里宴和商业试吃活动，页面应允许不同押金、清洁和公示规则，社区工作人员审批时能看到差异。

## 一键启动（Docker Compose）

```bash
# 环境已注入 COMPOSE_PROJECT_NAME 与 CC_PUBLISH_PORT，直接：
docker compose up -d --build

# 查看实际映射端口：
docker compose port app 8080
# 浏览器访问：
#   http://<宿主IP>:<CC_PUBLISH_PORT>/
# 容器内健康检查端点：/healthz
```

停止并清理：

```bash
docker compose down
```

> 本工程只有 app 一个服务（静态站点，无外部数据库依赖），compose **仅发布 app 端口**（`${CC_PUBLISH_PORT}:8080`）。
> 数据保存在浏览器 localStorage，点击侧边栏底部 ↺ 可随时恢复演示数据。

## 建议体验路径（一条完整业务流）

1. 用 `admin` 登录 → 工作台看到待核验/待验收/待办统计。
2. 打开「迎国庆邻里长桌宴」（待验收）→ 开始七项逐项验收，把「地面」标为不合格、「灶台」标为需补清洁，右侧自动**试算押金扣费** → 提交后生成押金决定。
3. 退出换 `wangxiulan` 登录 → 对扣费「提出押金争议」。
4. 换 `staff` 登录 → 协作任务台处理投诉、调解争议（调整扣费金额）→ 发布/更新社区公示。
5. 用 `wangxiulan` 新建一个「公益课堂」预约，勾选申请免押；再换 `staff` 审批，可看到与商业试吃在**押金/清洁/公示/告知**上的完整差异。
6. 用 `admin` 对使用中的公益课堂做事件处置：设备损坏派给 `repair` 定损（自动累加设备损耗度），修复后在「设备资源」页可见变化。
7. 「运营复盘」页查看按活动类型的场次、事件、补清洁工时、投诉、设备损耗排行与单次使用综合影响分。

## 功能与需求对照

| 需求点 | 实现位置 |
| --- | --- |
| 预约记录人数/烹饪类型/油炸/暂存/设备/性质/负责人/押金 | 新建预约页（五步表单，油炸触发专项告知，设备展示可用数量） |
| 预约成功后展示灶台/烤箱/冰箱/消毒柜/餐具/分类点 + 清洁要求 | 详情页「分配资源与清洁要求」：管理员核验时从具体设备中分配并做**同时段冲突/维修状态校验**，附 7 项清洁要求 |
| 使用前核验预约人/健康承诺/食材/设备 | 使用前核验弹窗四项勾选 + 活动前检查拍照；任一硬性项不过不能开始 |
| 使用中六类事件、五角色协同 | 上报事件（油烟/损坏/投诉/混放/加人/超时）按默认角色指派，可改派、闭环留痕；协作任务台有跨角色看板 |
| 七项逐项验收 + 押金退还/扣费/补清洁/限制预约 | 验收组件（灶台/台面/冰箱/垃圾/地面/餐具/设备），七项初始为「未检查」须**逐项显式选择**；问题项必填描述、不合格项强制拍照、总评必填，未完成七项提交按钮禁用，store 层二次兜底——**空操作不改变预约状态、不生成押金决定**；通过后按活动费率自动试算，可限制后续预约 |
| 数据隔离 / 越权防护 | 居民只能查看**本人**预约完整记录（直接输入他人预约 hash 显示无权限面板）；保洁/维修仅可见分派给本角色事件所关联的预约；列表、任务台跨角色看板、设备占用明细、复盘页均按角色收敛；管理员/社区工作人员因职责全量可见。`npm run security-check` 运行 `scripts/security-check.ts`，共 75 项自动化回归（越权访问、空验收拦截、暂存处置与押金联动、取消滞留与真实超时分类） |
| 按活动类型/设备损耗/清洁超时/投诉复盘 | 运营复盘页：KPI、分类条形图、损耗排行、清洁超时表、投诉跟踪、单次使用综合影响 TOP |
| 活动前检查 / 现场拍照 | PhotoCapture：手机调起摄像头（`capture="environment"`），本地 canvas 压缩；无摄像头可用 emoji 占位图走完全流程 |
| 押金争议 | 预约人发起 → 社区工作人员调解（成立全退 / 调整扣费 / 维持） |
| 公益免押 | 公益课堂押金 0 且可申请免押，社区工作人员核准；验收时免押结算、赔偿另追偿、补清洁由社区保洁承担 |
| 食品安全告知 | 新建预约必读必签；集体分餐留样 48h、商业活动需健康证明与食材票据等差异化条款 |
| 食材暂存与超时提醒 | 入库登记**格位/类别/标签/负责人/电话/预计取走时间**。工作台把提醒严格分两类：只有超过预计取走 2 小时的才进「⏰ 食材暂存超时提醒」（正数时长）；活动取消但取走时间未到的进「🚫 活动取消待处置食材」（显示剩余时长，**不报超时、不出现负数**）。管理员可**通知负责人（电话/短信/现场）→ 转待处理（10 元/天占位费）→ 报废 / 取回 / 清空**。**肉类/海鲜**只允许依规报废（60 元，责任提示+拍照）或签收取回，不得简单清空；普通报废 30、清空 20，费用计入押金（取消活动即时落账、验收时合并）；**公益课堂可豁免处置费**但仍记录责任；验收前在库食材须全部处置完毕 |
| 社区公示 | 按规则差异化（公益默认成果公示/邻里宴前后公示/**商业前置 3 天**），可同步线下公示栏、记录邻里反馈 |
| 三类活动不同押金/清洁/公示规则，审批可见差异 | `src/rules.ts` 集中配置：公益 ¥0 免押 / 邻里宴 ¥200 / 商业 ¥800，审批角色、时长上限、费率各不相同，审批页与详情页显著展示 |

## 目录结构

```
src/
├── types.ts               # 全部领域模型（预约状态机/事件/验收/争议/公示…）
├── rules.ts               # 三类活动差异化规则、食安告知书、清洁 7 项要求
├── seed.ts                # 演示账号与 7 条覆盖全生命周期的预约数据
├── router.ts              # 极简 hash 路由
├── stores/
│   ├── auth.ts            # 登录/角色（Pinia + localStorage）
│   └── kitchen.ts         # 预约/审批/核验/事件/验收/押金/争议/公示/复盘统计
├── components/            # 弹窗、时间线、现场拍照、事件卡片、七项验收表单
└── views/                 # 工作台、预约列表/新建/详情、设备、任务台、公示、复盘
```
